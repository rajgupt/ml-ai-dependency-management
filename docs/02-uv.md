# M2 · uv as your one tool 🟢🔵

> ⏱ 25 minutes · Route: Full, Fast, Notebook-first

## 3 a.m. story

*Your repo has a `requirements.txt`, a `requirements-dev.txt`, an
`environment.yml` that hasn't been touched in a year, a `setup.py`, and a
`Makefile` that calls `conda` and then `pip` in the same shell. Nobody knows
which one is true. The answer is: none of them.*

## What's actually going on

The 3 a.m. story above is the normal state of an ML repo: a pip file, a conda
file, a `setup.py`, and a `Makefile` that stitches them together with shell
glue nobody wants to touch. Each tool owns a slice — pip does packages, conda
does packages and some system libs, `pyenv` does the interpreter — and the
seams between them are where "which file is authoritative" bugs live.

`uv` collapses that into one tool that owns the interpreter, the
environment, resolution, the lock, and running your code. One command to add
a dependency, one file that's the truth about what you support, one file
that's the truth about what you ran. This module is the complete surface
you'll need — nothing later in the book reaches for a different tool at
layers 3 or 4. The alternatives (Poetry, pip-tools, conda, pixi) are real
and the [comparison appendix](appendix/tool-comparison.md) is honest about
where each one wins. The course still commits to `uv` throughout, so you
spend your three hours learning the concepts instead of shopping for tools.

## 🍳 Recipe 1 — the daily loop

```bash
uv init myproj && cd myproj      # new project: pyproject.toml, src layout, git
uv add requests                  # add a runtime dependency
uv remove requests                # remove one
uv lock                          # re-resolve, write uv.lock
uv sync                          # make .venv match uv.lock exactly
uv run python train.py           # sync-if-needed, then run inside the env
```

The interpreter is a dependency too, and it's the one people forget to pin:

```bash
uv python install 3.12   # download and manage a CPython build yourself
uv python pin 3.12       # write .python-version — this project uses 3.12
```

`requires-python` in `pyproject.toml` (written by `uv init --python`) says
which interpreter versions the project *allows*; `.python-version` says
which one you *actually use* day to day. You want both.

The loop underneath everything else in this book:

```
edit pyproject.toml → uv lock → uv sync → uv run
```

You rarely type `uv lock` and `uv sync` by hand — `uv add`/`uv remove` do
both for you, and `uv run` does the sync step automatically. You reach for
them directly when you've hand-edited `pyproject.toml`, or when CI needs the
explicit, non-mutating checks in Recipe 2.

## 🍳 Recipe 2 — lockfiles that actually reproduce

A trustworthy lock has three properties: exact versions (not ranges), a
hash of every package so a swapped artifact on the index is detected, and
resolution for every platform/Python combination the project supports — not
just the one you happened to run `lock` on.

`uv.lock` is universal: one file covers every platform, no
`requirements-linux.txt` / `requirements-mac.txt` split.

| Format | Hashes? | Cross-platform? | Standard? | Who reads it |
|---|---|---|---|---|
| `uv.lock` | yes | yes, one file | uv-specific | `uv` |
| `requirements.txt` | no | no (one platform's resolution) | de facto | `pip`, everything |
| `requirements.txt --generate-hashes` | yes | no | de facto | `pip` in strict/CI mode |
| `pylock.toml` (PEP 751) | yes | depends how it was exported | **yes, PEP standard** | any PEP 751-aware installer |

The CI contract is two flags, and they check different things:

```bash
uv sync --frozen    # install exactly what the lock says, never re-resolve
uv sync --locked    # first verify the lock still matches pyproject.toml,
                     # fail loudly if it doesn't, then install
```

Use `--locked` in CI — it's the one that catches "I edited `pyproject.toml`
and forgot to run `uv lock`" before it becomes a confusing failure three
steps later. Use `--frozen` in a Dockerfile, where the lock is already known
good and you're optimizing for a cached, deterministic layer.

For the teammate (or CI system) not on `uv`:

```bash
uv export --format pylock.toml -o pylock.toml       # PEP 751, the standard
uv export --no-hashes --no-dev -o requirements.txt   # the universal fallback
```

Say this plainly, because teams forget it: **these are exports, not sources
of truth.** Regenerate them from `uv.lock` whenever it changes; never
hand-edit `requirements.txt`. The moment someone edits the export directly,
you have two files claiming to be authoritative and no way to tell which one
actually ran.

## 🍳 Recipe 3 — dependency groups vs extras

This is the distinction most teams get backwards, so get the vocabulary
exact before the commands:

- **`[project.optional-dependencies]`** (PEP 621) — **extras**. Ship with
  your package. A user opts in: `pip install churnkit[gpu]`. For real,
  optional *features* of the thing you publish.
- **`[dependency-groups]`** (PEP 735) — **groups**. Never ship. Only for
  people working *on* the repo — `dev`, `docs`, `lint`, `typing`. Invisible
  to anyone who installs your project.

One line, worth more than the rest of this section: **extras ship, groups
don't.**

```bash
uv add --group dev pytest ruff        # dev tooling — never reaches production
uv add --optional gpu "torch>=2.6"    # a real feature users can opt into

uv sync --no-dev                      # what your production image should install
uv sync --all-extras --all-groups     # everything, for local development
```

Briefly, the history: before PEP 735 every tool invented its own dev-deps
table — `[tool.poetry.dev-dependencies]`, `[tool.uv.dev-dependencies]`, a
`requirements-dev.txt` convention that meant nothing outside that one repo.
`[dependency-groups]` is now a standard any tool can read, so prefer it over
tool-specific dev-dependency tables even outside `uv`.

## 🍳 Recipe 4 — tools that aren't project dependencies

`ruff`, `pre-commit`, `jupyter`, `huggingface-cli` — you run these, but your
*project* doesn't depend on them the way it depends on `torch`. Adding them
to `dependencies` or even a `dev` group means every contributor's resolver
has to account for them, and your lock grows with tools that have nothing
to do with what ships.

```bash
uv tool install ruff       # install once, isolated, available on PATH as `ruff`
uvx ruff check .           # run once, ephemeral — installs nothing permanent
```

`uvx` is to CLI tools what `npx` is in the JS world: try something once
without committing to it. `uv tool install` is for the CLI tools you reach
for daily across many projects. Either way, they stay out of the project's
lock — which keeps the production dependency tree small and honest, and
means a linter version bump never shows up in a `uv.lock` diff for a
training pipeline.

## 🍳 Recipe 5 — when resolution fails

A `uv` resolution error names the conflicting chain directly — read it top
to bottom, it's telling you exactly which two requirements can't both hold:

```
error: Because myproj depends on transformers>=4.40 and
transformers>=4.40 depends on tokenizers>=0.19, and myproj depends
on tokenizers<0.19, we can conclude that myproj's requirements are
unsatisfiable.
```

That's not uv being difficult — that conflict existed in your dependency
graph before you ran the command. Fixes, roughly in order of preference:

1. **Relax your own bound first.** Half the time the conflict is a range you
   set months ago for a reason that no longer applies.
2. **`uv lock --resolution lowest-direct`** to sanity-check your declared
   floors are actually real — it resolves to the *lowest* version that
   satisfies each direct dependency, which surfaces a `>=1.5` you wrote but
   never actually tested against.
3. **A constraints file** for transitive pins you don't own directly —
   `uv pip compile --constraint constraints.txt` or `[tool.uv] constraint-dependencies`
   pins a sub-dependency without adding it to your own requirements.
4. **`[tool.uv] override-dependencies`** — the last resort. It forces a
   version regardless of what the graph says, so it can produce an
   environment that genuinely doesn't work at runtime. If you use it, add a
   comment saying why and what would let you remove it.

## ⚠️ Sharp edges

- **`uv pip install` is the pip-compatibility API, not the project workflow.**
  It installs into the active environment but does **not** touch
  `pyproject.toml` or `uv.lock` — use it for a scratch/proof environment
  (like Lab 2's install-the-wheel step), never inside a project you intend
  to keep reproducible. Use `uv add` there instead.
- **`--frozen` skips the staleness check; `--locked` enforces it.** They are
  not interchangeable safety levels — CI wants `--locked` so a forgotten
  `uv lock` fails the build instead of silently shipping stale dependencies.
- **An exported `requirements.txt` is a snapshot, not a subscription.** It
  goes stale the moment `uv.lock` changes again, silently, with no warning
  from either file. Regenerate it as part of your release process, not by
  memory.

## ✅ Check yourself

<details>
<summary><code>ruff</code> — extra, dev group, or <code>uv tool</code>? Why?</summary>

Depends on who needs it to match. If the whole team must run the same
linter version (usually true — a version bump changes what CI flags), it's
a `dev` group dependency: `uv add --group dev ruff`. If it's purely your
personal preference and not enforced project policy, `uv tool install ruff`
or `uvx ruff`. It is never a runtime `dependencies` entry or an extra —
nobody running your trained model needs a linter installed.
</details>

<details>
<summary>CI installs with <code>uv sync --frozen</code>. A teammate adds a dep to <code>pyproject.toml</code> but forgets <code>uv lock</code>. Does CI catch it? Which flag would?</summary>

No, `--frozen` won't catch it — it installs straight from `uv.lock` without
ever comparing it to `pyproject.toml`, so CI builds an environment that's
silently missing the new dependency and fails later, somewhere confusing
that has nothing to do with the real cause. `--locked` is the flag that
catches it: it verifies the lock still satisfies `pyproject.toml` before
installing anything, and fails immediately with a message that names the
actual problem.
</details>
